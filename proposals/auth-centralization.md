# Централизация auth: предложение

## TL;DR

Сейчас auth-флоу (подключение кошелька, подпись, выдача токенов) реализован независимо в `web`, `marketplace`, `time-tracker`, legacy-фронте. Любое изменение в auth — новый провайдер, фикс уязвимости, обновление SDK — приходится повторять во всех сервисах. Уже наблюдается дрейф: разные наборы wallet-провайдеров, разные методы коннекта между нашими же продуктами.

Предлагается выделить auth в отдельный сервис (`auth.app.com`) и общий пакет (`@app/auth-core`), которые потребляют все остальные фронты. Разовая инвестиция ~10–16 человеко-дней, окупаемость на 3–4-м auth-изменении (≤ 6–12 месяцев при текущей частоте задач).

---

## 1. Что произошло

В `web` только что завершена миграция Solana-аутентификации с Reown на нативный `@solana/wallet-adapter-react`. Изменения затронули ~8 файлов в одном сервисе.

Та же миграция теперь подлежит выполнению в `marketplace`, `time-tracker` и legacy-фронте — отдельно, в каждом сервисе, с одинаковой логикой и теми же рисками.

## 2. Системная проблема

Auth-логика (Effector-модели, wallet-провайдеры, обработка nonce/подписи, токены) **дублируется** в каждом фронте. Это даёт два класса издержек:

**Для разработки.** Любое изменение auth — добавление wallet-провайдера, апдейт SDK, фикс CVE, корректировка флоу — умножается на число сервисов. Нет единой точки правки.

**Для пользователя.** Уже сейчас между сервисами наблюдается расхождение: разные наборы поддерживаемых кошельков, разные способы коннекта (где-то доступно браузерное расширение, где-то только QR с мобильного). С точки зрения юзера, переходящего между нашими продуктами, это выглядит как несогласованность экосистемы. По мере роста числа сервисов и провайдеров расхождение будет только нарастать.

## 3. Сценарий "ничего не меняем"

Стоимость дублирования платится в трёх валютах:

| Валюта | Что происходит |
|---|---|
| **Время разработки** | Каждое изменение auth × N сервисов. Solana-миграция, выполненная сейчас в одном сервисе, ждёт повторения в остальных. Следующий провайдер/чейн/обновление — снова × N. |
| **UX и удержание** | Юзер в `marketplace` подключился кошельком A; в `time-tracker` он же недоступен — приходится регистрировать другой кошелёк или уходить. Тикеты в саппорт + молчаливый абандонмент. |
| **Безопасность** | Найденная уязвимость в wallet-SDK или в логике токенов фиксится последовательно в N местах. Высокий риск, что в одном из сервисов фикс будет забыт или отложен. |

Эти издержки **не одноразовые** — они линейно растут от количества (изменений × сервисов) и накапливаются с каждым новым сабдоменом и каждым новым провайдером.

## 4. Предлагаемое решение

Двухкомпонентная архитектура:

### `@app/auth-core` — общий пакет (workspace dep)

Чистая библиотека: Effector-модель, hooks (`useAuth`, `useUser`), API-клиент, типы. Потребляется каждым фронтом. Сервисы **не знают** про Reown / wallet-adapter / TON-Connect — они только читают сессию и при её отсутствии редиректят на auth-фронт.

### `apps/auth` — отдельное приложение (`auth.app.com`)

Тонкий Vite-фронт, единственное место, где живёт **логика логина**: модалка выбора кошелька, обработка nonce, подпись для аутентификации, выдача сессии. Сюда же — самые тяжёлые части wallet-стека (`@reown/appkit`, выбор провайдера, обработка ошибок коннекта).

Продуктовые сервисы (marketplace, time-tracker, etc.) сохраняют минимальный wallet-инстанс **только для подписи on-chain транзакций** — это техническое требование non-custodial web3-архитектуры: подписи происходят на фронте через расширение кошелька, ключ никогда не покидает устройство пользователя. Эта часть кода остаётся в сервисах, но она тонкая (без модалок выбора, без обработки логин-флоу) и при желании выносится в отдельный shared-пакет (`@app/wallet-kit`) как следующий шаг.

Главный профит: вся **логика аутентификации** — в одном месте; следующий wallet-провайдер (новый кошелёк, новый чейн) добавляется один раз в `auth-app`, а не N раз в N сервисах.

### Cookie-based session на `.app.com`

Сессия хранится в HttpOnly-куке на корневом домене `.app.com` → автоматически шарится между `marketplace.app.com`, `time-tracker.app.com`, `auth.app.com` и т.д. Это техническое требование архитектуры: localStorage привязан к exact origin и сессию шарить не умеет в принципе.

```
[ marketplace.app.com ] ─┐
[ time-tracker.app.com ] ─┤  ── редирект на auth.app.com если нет сессии
[ legacy.app.com ]        ─┤      ↓
                                 [ auth.app.com ]
                                  ├─ форма входа
                                  ├─ wallet-провайдеры
                                  └─ выпуск HttpOnly-cookie на .app.com
                                      ↓
[ marketplace / time-tracker / ... ] ── читают сессию из общей куки
```

## 5. Оценка трудозатрат

Разовая инвестиция:

| Шаг | Оценка |
|---|---|
| Извлечь `@app/auth-core` из текущего `web` | 1–2 дня |
| Поднять `apps/auth` (Vite-приложение поверх `auth-core`) | 1–2 дня |
| nginx + docker + DNS `auth.app.com` | 1 день |
| Бэк: HttpOnly-куки на `.app.com`, CORS с credentials, ротация refresh-токенов | 2–5 дней |
| Миграция `web` / `marketplace` / `time-tracker` / legacy на `@app/auth-core` | 2–4 дня (≈ 0.5–1 день на сервис) |
| Тестирование cross-subdomain flow и edge cases | 1–2 дня |
| **Итого** | **≈ 10–16 дней** |

**После миграции** каждое изменение auth — ≈ 1 день в одном месте.

**Точка окупаемости.** Дельта между «текущий путь» и «новый путь» на одно изменение — ≈ 2–4 дня экономии. Разовая инвестиция окупается на **3–4-м auth-изменении**. С учётом, что только что закончилось одно (Solana) и команда уже знает, что предстоят другие, горизонт окупаемости — **6–12 месяцев**.

## 6. Что требуется

- **Зелёный свет** на выделение времени под рефакторинг (~10–16 дней разработки).
- **Готовность бэка** перейти на cookie-based session: HttpOnly + Secure + SameSite + ротация refresh. Без этого cross-subdomain не работает, и предложение теряет смысл.
- Согласование DNS-настроек для поддомена `auth.app.com`.

## 7. Что НЕ предлагается

- Менять текущий `web` без причины — миграция инкрементальная, сервисы переезжают на `@app/auth-core` по одному.
- Переписывать auth-логику с нуля — она уже есть в `web`, её нужно только вынести.
- Менять backend-API за пределами cookie-механики и refresh-rotation.
- **Менять модель подписания транзакций.** Подпись on-chain операций остаётся на фронте через расширение кошелька (non-custodial) — это стандарт web3 и ожидание пользователей. Бэк не получает доступа к приватным ключам ни на одном из этапов. Централизация касается **только auth-флоу** (логин и сессия), но не самого использования кошелька в продуктовых сценариях.

---

## Альтернатива: оставить как есть

Тоже валидный сценарий, если горизонт жизни проекта < 6 месяцев или auth-изменения предполагаются редкими. В этом случае стоит зафиксировать решение явно — чтобы текущий тех. долг был осознанным, а не накопленным по умолчанию.
